# 0022. CI/CD

- **Status**: Accepted
- **Date**: 2026-10-29
- **Supersedes**: [0021](0021-deployables.md)

## Context and Problem Statement

ADR 0021 made the deployable the centre: what is built and shipped, what it talks to, where it runs. Pipelines were a side fact on it, stored as seven stage buckets and a set of tools, with no jobs, no order and no steps. A scripted Jenkinsfile read as "read in part" with nothing to say which part, and a Jenkinsfile that is one call to a shared library read as a pipeline that does nothing.

The questions architects and reviewers bring are about delivery itself: what starts each pipeline, what it runs in what order, what it hands to templates and libraries, what images it builds from which base, where it deploys, and what in the setup a reviewer would flag. The service-to-service map, read from configuration hosts, answered a different question and was rarely the one asked.

Measured before this was written, across every local workspace: 445 GitHub workflows in 45 repositories, 18 Jenkinsfiles in 6 (the long ones declarative, about 300 lines, and scripted, about 400 lines with shared libraries and stages built in loops), no GitLab file, and Rancher only as the target of `rancher login --context` and `rancher kubectl apply` in GitLab jobs.

## Decision Drivers

- **Evidence over verdicts**: facts with file and line; hygiene flags state what a file does, never a score.
- **Honest reading**: what a reader cannot follow is a row with a line range and a reason.
- **Offline and deterministic**: nothing is run or fetched; the same commit gives the same tables.
- **No new modules**: Groovy is tokenised by hand, YAML through `yaml.v3` nodes.

## Decision

1. **Pipelines first.** One fact model for every system: triggers → jobs (with needs) → steps, hand-offs, outputs and unread regions. A job is a GitHub or GitLab job, a Jenkins stage, an Azure job, a Bitbucket step, a CircleCI workflow job or a Fleet target. Ordered systems write their order as needs; depth is computed once, in the engine.
2. **The artifact stays, as the join.** Images, apps, functions, desktop and mobile apps are kept (renamed from deployables), joined to the steps that build and deploy them and to the code inside. Runtime links, environments as rows, configuration values and the dependency list are removed.
3. **Tier 1, read to a measured bar:** GitHub Actions, GitLab CI, Jenkins and Rancher. Each must read at least 95% of its corpus in full, resolve references to other repositories of the workspace, record one pipeline starting another, and follow deploy steps to the images they run. **Tier 2**, read into the same model: Azure, Bitbucket, CircleCI.
4. **Jenkins** is read from a call tree a small Groovy tokenizer builds. Unknown calls are shared library steps, with library `implicit` when no `@Library` names one; a `vars/name.groovy` in the workspace is read as that step's body. Stages built in a loop are jobs repeated over that loop's collection (`matrix` -1); a parallel map the file never fills is `dynamic_stages`.
5. **Rancher** is a deploy target inside any CI job (server and `cluster:project` context kept as written, environment from the job, then from per-environment variable names, then from the job's name), plus Fleet bundles as pipelines of their own and Rancher Pipelines files.
6. **Hygiene flags** are rows in `cicd_flags`, each rule with a template in `docs/rules/cicd.yml`.

### How each system maps

| System | Job | Order | Hand-offs | Gate |
|---|---|---|---|---|
| GitHub Actions | job | `needs` | `uses:` (pinned by sha, version or branch), `workflow_run` | `environment` |
| GitLab | job | stage order, `needs`, `needs:project` | `include` (local read in), `component`, `template`, `trigger` | `when: manual`, `environment` |
| Jenkins | stage | order written; parallel branches share their start | `@Library`, library steps, `load`, `build job:` | `input` |
| Rancher Fleet | target | — | `helm.chart` | — |
| Rancher Pipelines | stage | order written | catalog apps | — |
| Azure | job | stage order, `dependsOn` | `template` | deployment `environment`, `ManualValidation` |
| Bitbucket | step | order written, `parallel` | `pipe` | `trigger: manual`, `deployment` |
| CircleCI | workflow job | `requires` | orbs | `type: approval` |

## Consequences

- The snapshot contract breaks on purpose: revision 16 removes nine tables. Older snapshots keep them; the UI reads what a snapshot has.
- Tier 2 systems may lag tier 1; the corpus runner (`go run ./extensions/cicd/cmd/corpus`) measures every system the same way.
- The call map between services is gone from the engine; a revival would start from configuration readers kept in git history.
